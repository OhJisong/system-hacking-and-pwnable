1. 포너블(pwnable)과 시스템 해킹 개요
1-1. 시스템 해킹이란?

시스템 해킹(System Hacking)
→ “프로그램이나 시스템의 취약점을 분석하고, 이를 이용해 권한을 상승시키거나 임의의 코드를 실행하는 일련의 과정”

대상은 운영체제, 응용 프로그램, 서버 프로세스 등이고, 목표는 예를 들면:

일반 사용자 권한 → root 권한 상승

원래 프로그램이 의도하지 않은 코드 실행

인증 우회, 민감 정보 탈취 등

슬라이드에서도 “지피티 피셜 시스템 해킹 분야”라고 하면서 굉장히 넓다는 걸 강조하고, 이번 세션에서는 그 중에서도 포너블(pwnable) 에 집중한다고 밝힌다. 

시스템해킹_1주차(공유용)_수정

1-2. 포너블(pwnable)이란?

정의 (슬라이드 기준 요약)

“시스템 해킹 분야의 한 갈래로, 프로그램의 메모리 취약점을 이용해 시스템을 장악하거나 동작을 조작하는 기술”

주로 다루는 것:

운영체제나 프로그램의 보안 취약점 분석 → 공격

관리자 권한 획득, 프로그램 흐름을 해커 마음대로 바꾸기

CTF(해킹 대회)에서 pwnable 문제 유형으로 자주 출제됨.

즉, 시스템 해킹 전체 중에서, ‘바이너리/메모리 취약점 쪽’에 집중된 실습 분야라고 보면 된다.

1-3. 포너블이 중요한 이유

슬라이드에서 4가지 포인트로 정리되어 있음:

해킹 체험

“시스템을 어떻게 뚫을 수 있는지” 실제로 경험할 수 있는 분야.

단순 이론이 아니라, gdb, pwntools로 직접 익스플로잇을 짜보게 됨.

실전 보안에 꼭 필요한 역량

포너블은 곧 **취약점 분석 + 침투 테스트(pen-test)**에 쓰이는 기술.

보안 직무, 레드팀, 분석 연구실에서 매우 중요하게 봄.

CTF 대회 스킬셋

대부분의 CTF에서 웹, 리버싱, 크립토와 함께 pwnable 카테고리가 반드시 있음.

동아리 내 대회/외부 CTF에서 활약하려면 필수 역량.

시스템 내부 이해 (사고력 향상)

메모리 구조, 함수 호출, 스택 프레임 같은 컴퓨터 구조/운영체제 지식을 몸으로 익히게 됨.

이후에 리버싱, 악성코드 분석, 커널 보안 등으로 확장할 때 토대가 됨.

3. 프로그램 메모리 구조 – 4영역

이 부분이 1주차 핵심 중 하나.

3-1. 전제: 지금 말하는 “메모리”는 RAM

슬라이드에서 “지금 말하는 메모리는 RAM, 디스크 아님!” 이라고 강조.

실행 파일은 원래 디스크에 있지만, 실행되는 순간 메모리(RAM)로 적재되어 4영역 구조를 형성.

3-2. 네 가지 주요 영역

코드(Code / Text Segment)

컴파일된 실행 코드(기계어)가 저장되는 영역.

각 함수의 명령어, 분기/점프 등 제어 흐름 명령 포함.

일반적으로 읽기 + 실행 권한만 있고, 쓰기 권한은 없음
→ 코드 영역에 데이터를 쓰지 못하게 해서 보안 강화 (W^X 원칙과 연결).

데이터(Data Segment)

실행 시 사용되는 전역 변수, 정적 변수가 들어가는 영역.

세분화됨:

.data : 초기화된 전역/정적 변수

예) int g = 3;

.bss : 초기화되지 않은 전역/정적 변수

예) int g2; (초기값을 안 준 경우)

.rodata : 읽기 전용 데이터 (상수)

예) 문자열 상수 "hello" 같은 것들.

힙(Heap)

프로그램 실행 중 동적으로 메모리를 할당/해제하는 영역.

보통 낮은 주소 → 높은 주소 방향으로 확장.

C 기준 함수:

malloc, calloc, realloc 등으로 할당

free로 해제

사용자가 해제를 안 하면 메모리 누수(memory leak) 발생.

스택(Stack)

함수 호출 시 사용되는 메모리 영역.

지역 변수, 함수 인자, 반환 주소, 저장된 레지스터 값 등이 저장됨.

높은 주소 → 낮은 주소 방향으로 자라나는 구조.

함수마다 스택 프레임(stack frame) 을 하나씩 가짐.

슬라이드에는 네 영역 구조가 그림으로 나와 있고, 어떤 변수/데이터가 어디에 들어가는지 시각적으로 보여줌. 

시스템해킹_1주차(공유용)_수정

3-3. 스택에 저장되는 것은?

퀴즈1에서 “다음 중 스택에 저장되는 것을 모두 고르세요.” 라고 물어보는 슬라이드가 있었음.

항목 예시:

stdio.h, stdlib.h – 헤더 파일(코드/라이브러리 관련, 스택 아님)

global1, global2 – 전역 변수 → 데이터 영역(.data/.bss)

x, y – 함수 안의 지역 변수라면 스택

call_count – 함수 밖에서 정의된 정적/전역이면 데이터 영역, 함수 안 static이면 역시 데이터 쪽

size – 함수 인자로 들어오면 스택(인자)

local_ptr – 지역 포인터 변수 → 스택

a, b, c – 역시 지역 변수라면 스택

"meow ^._.^" – 문자열 상수 → .rodata

핵심 결론:
“지역 변수 + 함수 인자”는 스택, “전역/정적/상수”는 데이터/rodata
라고 기억하면 된다.

4. 레지스터 개념
4-1. 레지스터란?

CPU 내부에 있는 아주 빠른 임시 저장소

용도:

연산 결과 임시 저장

메모리 주소 보관

현재 실행 중인 명령어 위치 저장

스택 최상단, 기준점 표시 등

메모리(RAM)보다 훨씬 빠르기 때문에, 어셈블리에서 거의 모든 연산은 레지스터 중심으로 이루어진다.

4-2. 레지스터 종류(분류)

슬라이드 기준 주요 분류:

범용 레지스터 (General-purpose)

여러 용도로 사용 가능한 레지스터

x86 32bit 기준: EAX, EBX, ECX, EDX 등

연산, 임시 저장, 주소 계산 등에 사용

세그먼트 레지스터 (Segment)

코드/데이터/스택 세그먼트의 베이스 주소 보관

예전 16bit 세그먼트 구조에서 중요했지만, 현대 x86-64에서는 상대적으로 비중이 줄어듦.

포인터 레지스터 (Pointer)

스택 포인터, 베이스 포인터, 명령어 포인터 등

스택 프레임이나 현재 실행 위치를 가리키는 데에 특화된 레지스터들

인덱스 레지스터 (Index)

배열/문자열 처리에 쓰이는 인덱스 역할

반복문에서 주소 계산에 자주 사용

플래그 레지스터 (Flag)

연산 결과(Zero Flag, Carry Flag 등)와 CPU 상태를 저장

분기/조건문에서 중요한 역할

4-3. 우리가 특히 알아야 하는 레지스터 4개

슬라이드에서 “이 친구들을 알아야 해요”로 강조한 것:

ESP / RSP – Stack Pointer

현재 스택의 최상단(top)을 가리키는 포인터.

32bit: ESP, 64bit: RSP.

EBP / RBP – Base Pointer

현재 함수의 스택 프레임 기준점.

보통 EBP를 기준으로 인자/지역 변수에 접근.

EIP / RIP – Instruction Pointer

지금 실행 중인 명령어의 주소.

call, ret, jmp 등에 의해 값이 바뀌며, 프로그램 흐름을 결정.

EAX / RAX

연산 결과 또는 함수 리턴 값을 담는 용도로 관습적으로 사용.

요약하면:

ESP/RSP → 스택 맨 위
EBP/RBP → 현재 함수의 기준점
EIP/RIP → 다음에 실행할 명령어
EAX/RAX → 함수 리턴값 / 연산 결과

를 기억해두면, 나중에 gdb로 디버깅할 때 스택 프레임을 이해하기가 훨씬 쉬워진다.

5. 함수 호출 시 스택 변화 (cdecl 기준)

이 부분은 슬라이드가 그림으로 엄청 상세히 설명하는 핵심 파트.

5-1. 함수 호출 규약(calling convention)

슬라이드에서는 x86 32bit, cdecl 기준으로 설명:

함수 인자를 오른쪽에서 왼쪽 순서(right-to-left) 로 스택에 push

함수 리턴 값은 EAX 레지스터에 저장

스택에 쌓인 인자를 호출자(caller) 가 정리함

5-2. main 함수 시작 시 스택

운영체제가 프로그램을 실행하면, 런타임이 main을 호출하면서 초기 스택 프레임을 만든다.

대략 구조:

최상단 근처:

Return Addr : main이 끝나면 점프할 OS 런타임의 주소

Previous EBP : 이전 프레임 포인터(런타임이 세팅)

그 아래로 main에서 사용하는 지역 변수 들이 차례로 스택에 자리 잡는다.

슬라이드 예시에서는 local: a, b, c 같은 변수들이 EBP 기준 아래에 쌓여 있는 구조를 그림으로 보여줌.

5-3. 인자 전달 & 함수 호출

예를 들어 sum(a, b) 를 호출한다고 하자.

main 에서 지역 변수 a = 2, b = 3 등이 이미 스택에 할당됨.

sum(a, b) 호출 시:

먼저 b (두 번째 인자) push → Arg y

그 다음 a (첫 번째 인자) push → Arg x

call sum 실행:

CPU가 현재 EIP 값을 스택에 push → 이것이 Return Addr (sum이 끝난 후 돌아올 곳)

이 순간 스택의 위쪽에는:

Arg x (a 값)
Arg y (b 값)
Return Addr (sum이 끝나면 돌아갈 주소)

가 쌓여 있다.

5-4. sum 함수 진입 후 스택 프레임 생성

sum 함수가 시작되면 어셈블리 상에서 흔히 이런 코드가 실행됨:

push ebp        ; 이전 EBP 저장
mov  ebp, esp   ; 현재 스택 위치를 EBP로 설정
sub  esp, N     ; 지역 변수 공간 확보


이 과정을 스택 관점에서 보면:

push ebp

Previous EBP 가 스택에 저장됨 (현재는 main의 EBP 값)

mov ebp, esp

이제 EBP 가 새 스택 프레임의 기준점이 됨

sub esp, N

local 변수들을 위한 공간이 생김 (esp가 더 낮은 주소로 이동)

이후 sum 함수 내부에서 사용하는 지역 변수들은 EBP를 기준으로 음수 오프셋으로 접근 ([ebp-4], [ebp-8] 등).

5-5. sum 함수 리턴 직전 & 리턴 후

sum에서 계산이 끝나면 결과를 EAX에 담는다.
예: EAX = a + b = 5

leave / ret 시퀀스가 실행되면서:

mov esp, ebp

ESP 를 프레임 기준점으로 되돌림

pop ebp

스택에서 Previous EBP를 꺼내와 원래 main의 EBP로 복구

ret

스택 최상단에 있던 Return Addr를 EIP로 가져와 그 주소로 점프

동시에 스택 포인터가 인자 직전 위치로 이동

리턴 후에는:

main의 스택 프레임만 남고, EAX에 있는 5 값을 c 같은 변수에 저장 (c = sum(a, b);)

슬라이드에서 “sum 리턴 → main에서 c = 5 저장” 이라는 그림으로 설명.

5-6. 퀴즈2 – mult() 스택 프레임에 push되는 순서

보기:

Previous EBP

Return Addr

Argv: a

Argv: b

Local: result

cdecl 기준 push 순서를 생각하면:

호출자에서 인자를 오른쪽→왼쪽 순으로 push

Argv: b

Argv: a

call mult 실행 시 CPU가 Return Addr 를 push

mult 함수 진입 후 push ebp 로 Previous EBP 저장

로컬 변수는 sub esp, N 처럼 공간만 확보하는 경우가 많지만,
“스택에 새로 생기는 순서” 관점에서 보면 맨 마지막에 Local: result 자리까지 내려감.

그래서 스택에 쌓이는 순서를 나열하면:

Argv: b → Argv: a → Return Addr → Previous EBP → Local: result

라고 볼 수 있다(강의에서 의도한 정답도 이 순서일 가능성이 높음).
